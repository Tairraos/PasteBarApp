# Internationalization (i18n)

> Last verified: 2026-09-16 · Branch `harnessing`
> Scope: the two translation systems, the build-time locale loader, adding keys, and the
> audit tooling. Backend YAML is also described in
> [`database-migrations.md`](database-migrations.md) only insofar as migrations seed settings.

## 1. Two translation systems

PasteBar has **two independent translation stores** with no shared source of truth:

|           | Backend                                                    | Frontend                                                  |
| --------- | ---------------------------------------------------------- | --------------------------------------------------------- |
| File      | `src-tauri/src/services/translations/translations.yaml`    | `packages/pastebar-app-ui/src/locales/lang/<lang>/*.yaml` |
| Loaded    | compile time, `include_str!`                               | build time, Vite plugin → virtual module                  |
| Reader    | `Translations::get(key)`                                   | i18next `t()` / `<Trans>`                                 |
| Scope     | **native OS surfaces**: tray menu, window/menu item labels | **everything rendered inside the webview**                |
| Languages | 2 flat maps (`en`, `zhCN`)                                 | 2 catalog directories (`en`, `zhCN`)                      |
| Keys      | 8 flat dotless keys                                        | nested namespaces, thousands of keys                      |

### Backend: `translations.rs` + `translations.yaml`

`translations.yaml` is a flat two-level YAML: a language code, then a flat key → string map.
The `en` block holds 9 keys (`translations.yaml:1-10`): `add_first_item_here`,
`disable_history_capture`, `enable_history_capture`, `clipboard_image_size`,
`history_capture_is_disabled`, `recent_history`, `open_pastebar`, `unlock_pastebar`, `quit`.

The struct `Translations` (`translations.rs:6-17`) declares one `HashMap<String, String>`
field per language. The YAML is embedded and parsed at compile time
(`translations.rs:21-24`), so a malformed file is a **compile-time** failure.

Language is global mutable state: `CURRENT_LANGUAGE` is a `static Lazy<RwLock<String>>`
defaulting to `"en"` (`translations.rs:19`). `Translations::set_user_language` (`:27-30`)
overwrites it; `Translations::get` (`:32-41`) reads it and returns the mapped string, or the
literal `"Translation for '<key>' not found."` on a miss.

Two caveats:

- **`CURRENT_LANGUAGE` defaults to `"en"`, not to the user's language.** It is set once at
  startup from the stored setting (`src-tauri/src/main.rs:560`) and again whenever the frontend reports a
  change (`src-tauri/src/commands/translations_commands.rs:24`). If neither runs, the tray falls back to English
  while the webview shows Chinese. The fallback is deliberate: `get_lang`'s `_` arm returns
  `en` for any unrecognised code, so a stale `de` from an older install still yields readable
  menu labels instead of a `Language 'de' not supported.` string.
- `serde_yaml` deserialises into a struct with **all fields required**, so a language block
  present in the YAML but missing from the struct (or vice versa) is a hard parse error. The
  struct and the YAML must be edited together. The struct is now `en` + `zhCN`
  (`translations.rs:6-17`).

### Frontend: `locales/lang/` + i18next

The UI initialises i18next in `packages/pastebar-app-ui/src/locales/locales.ts`. Key settings
(`locales.ts:58-78`):

| Option                          | Value                                                              | Effect                                                |
| ------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------- |
| `resources`                     | `import resources from 'virtual:i18next-loader'` (`locales.ts:17`) | the whole bundled locale tree, injected at build time |
| `defaultNS`                     | `'common'`                                                         | bare `t('Foo')` resolves in the `common` namespace    |
| `keySeparator`                  | `':::'`                                                            | nested keys are split on `:::` — **not** on `.`       |
| `nsSeparator`                   | `false`                                                            | disables i18next's `:` namespace syntax               |
| `supportedLngs`                 | codes from `LANGUAGES` (`languges.ts`)                             | filters detection to known languages                  |
| `detection.order`               | `localStorage`, `cookie`, `navigator`                              | browser-style detection                               |
| `saveMissing` / `updateMissing` | `isDev`                                                            | missing-key capture only in dev builds                |

`keySeparator: ':::'` is the load-bearing detail: it is the same separator the Rust command
uses to split a parent key from a sub-key (§4), so the two systems agree on key shape even
though they store nothing in common. Because `nsSeparator` is `false`, a translation key
containing `:` will not be split into a namespace.

### How they interact

They do not share data; they share a **language code and a separator convention**:

1. The user changes language in the settings UI.
2. i18next emits `languageChanged` (`locales.ts:152-159`), which invokes **two** backend
   commands: `change_menu_language` (→ `Translations::set_user_language`) and
   `build_system_menu` (→ rebuild the native tray with the new strings).
3. From then on, in-webview strings come from the bundled frontend locales and native-surface
   strings come from the backend YAML.

So adding a string means deciding **which system owns it** and, for anything the OS renders,
adding it to both.

## 2. The Vite i18n loader plugin

The plugin is vendored under `src/lib/i18n-vite-loaded/` and registered in
`packages/pastebar-app-ui/vite.config.mts:105-108`:

```ts
i18nextLoader({
  paths: ['./src/locales/lang'],
  namespaceResolution: 'basename',
}),
```

**At build time**, `loader.ts` runs `loadLocales()` (`src/lib/i18n-vite-loaded/loader.ts:72-158`):

1. `resolvePaths` maps `./src/locales/lang` against `process.cwd()`; `assertExistence`
   throws if the directory is missing (`src/lib/i18n-vite-loaded/loader.ts:73-74`).
2. `enumerateLangs` treats **every subdirectory** of the locale path as a language code
   (`src/lib/i18n-vite-loaded/loader.ts:84`).
3. Inside each language directory, `findAll` globs `**/*.json`, `**/*.yml`, `**/*.yaml`
   (`src/lib/i18n-vite-loaded/loader.ts:91-94`); `loadAndParse` parses YAML via `js-yaml` or JSON by extension
   (`src/lib/i18n-vite-loaded/utils.ts:46-56`).
4. A namespace is built from the language plus the **basename** of the file joined with `.`
   — `namespaceResolution: 'basename'` makes `en/common.yaml` become `en.common`
   (`src/lib/i18n-vite-loaded/loader.ts:104-114`).
5. Bundles are deep-merged across directories with `ts-deepmerge`
   (`src/lib/i18n-vite-loaded/loader.ts:118`) — later paths win, though only one path is configured today.

**Emitted output** is a virtual module, `virtual:i18next-loader`
(`src/lib/i18n-vite-loaded/utils.ts:8-9`, resolved to `'\0' + id`). Rather than one JSON blob — the commented-out
approach at `src/lib/i18n-vite-loaded/loader.ts:123-124` — the plugin emits **named exports**, one per language, plus
a default `resources` object (`src/lib/i18n-vite-loaded/loader.ts:127-140`):

```js
export const en = { "common": { … } }
export const de = { … }
const resources = { "en": en, "de": de, … }
export default resources
```

Named exports are used because codes such as `zhCN` and `esES` are valid JS identifiers here,
whereas dashes would not be (`jsNormalizedLang` also replaces `-` with `_`).

Being virtual, the module is resolved on demand via `resolveId`/`load` (`src/lib/i18n-vite-loaded/loader.ts:162-178`),
and every contributing file is registered with `this.addWatchFile`, so `handleHotUpdate` can
invalidate the module and force a **full page reload** on a locale edit (`src/lib/i18n-vite-loaded/loader.ts:186-211`).
Editing a translation YAML in dev reloads the app rather than hot-swapping.

Net effect: locale YAML is **inlined into the JS bundle** at build time. There is no runtime
fetch of translation files, and a locale file added after a build is not picked up until the
next build.

## 3. Adding a translation key

### Frontend path (webview strings)

1. Pick the namespace file under `packages/pastebar-app-ui/src/locales/lang/en/` — the
   filename _is_ the namespace (`en.common`, `en.settings`).
2. Add the key to `en/` first; `en` is `DEFAULT_LOCALE` (`languges.ts:1`) and the fallback
   language (`locales.ts:47-51`).
3. Add the same key to every other language directory. The key separator is `:::`, not `.`:
   `MyGroup:::My New Label: My New Label` in `en/settings.yaml`.
4. Use it in a component as `t('My New Label')` for the default namespace, or
   `t('settings:::MyGroup:::My New Label')` for another.
5. Rebuild (`npm run build`) or rely on the dev-server full reload (§2).

### Backend path (native surfaces)

Only for strings the OS renders — tray menu, native menu items.

1. Add the key to **every** language block in
   `src-tauri/src/services/translations/translations.yaml`. A missing key is not a parse
   error; it degrades to the literal `"Translation for '<key>' not found."` at runtime.
2. If you add a **new language**, change the YAML, the `Translations` struct
   (`translations.rs:6-17`) **and** `get_lang` (`translations.rs:43-56`) together, or the
   parse fails / the language silently falls through to English.
3. Read it with `Translations::get("<key>")`, then rebuild — the YAML is embedded at compile
   time.

### The automatic dev-only path

In dev, the frontend _writes_ missing frontend keys into the YAML itself:

1. i18next's `missingKeyHandler` (`locales.ts:80-138`) fires for an unknown key, skipping
   only the `tours` namespace (`locales.ts:89-91`); disabled in production (`:81-83`).
2. It queues the miss into `missingKeys` and starts a **5-second interval** (`:131-137`).
3. `saveMissingKeysDevOnly` (`translation-utils.ts:24-41`) invokes the Rust command
   `update_translation_keys`.
4. `update_translation_keys` (`translations_commands.rs:33-141`) is **debug-build only**
   (`:35-37`) and writes each key to `"$MISSING_TRANSLATION_SAVE_PATH/<language>/<namespace>.yaml"`
   (`:48-51`), creating directories and re-serialising with sorted top-level keys (`:117,120-135`).

## 4. Checking translations

```bash
npm run translation-audit                                  # list keys used in code but absent from en/
node scripts/harness/i18n-ratchet.mjs                      # the gate form (ratcheted)
node scripts/harness/i18n-ratchet.mjs --report             # list every missing key
node scripts/harness/i18n-ratchet.mjs --update             # lower the baseline
```

`scripts/i18n-missing-keys.mjs` answers one question: **is every `t('…')` argument in the UI
present in the English catalog?** The English files are the key set (§1), so an argument with
no entry cannot be translated at all — i18next echoes it and the string stays English in a
Chinese-only UI.

This is deliberately a _different_ check from "does every locale agree with English". The
project previously shipped `scripts/translation-audit.ts` for the latter; it was removed
because with one target language it had nothing left to compare, and because it could not see
the failure that actually occurred: the settings screen called `t('Set system OS hotkeys …
Supports up to 3-key combinations.')` while `zhCN/settings2.yaml` defined the same sentence
**without** the trailing clause. Every file agreed with every other file, the audit was
silent, and the Chinese translation was never looked up.

**Parsing is the hard part, and this script is not a YAML parser.** Three forms in these
files defeat a naive `indexOf(': ')` scan, and each produced false positives before it was
handled:

| Form               | Example                                    | Naive result                                                   |
| ------------------ | ------------------------------------------ | -------------------------------------------------------------- |
| Indented sub-keys  | `Window:` + indented `Minimize Window`     | Reported missing; the lookup key is `Window:::Minimize Window` |
| Quoted keys        | `'Update: Permission Denied': …`           | Split mid-key at the colon inside the quotes                   |
| YAML explicit keys | `? 'Permission Check Failed: …'` + `: '…'` | Key read as `? 'Permission Check Failed`                       |

The first run reported **228**; after handling these forms and stripping quotes, it reported
**94**. A checker that over-reports is worse than no checker, so each case was fixed against
the real files rather than by loosening the rule.

`scripts/harness/i18n-ratchet.mjs` is the gate (baseline `docs/harness/i18n-baseline.json`,
currently **94**). The count may only go **down**. Those 94 are real defects — strings a
Chinese user sees in English — and the ratchet lets them be fixed incrementally while any
_new_ one fails immediately. Verified by lowering the baseline: the gate exits 1.

**What `MISSING_TRANSLATION_SAVE_PATH` controls.** Nothing above. It is read by **Rust**,
`src-tauri/src/commands/translations_commands.rs:39`, as the base directory for the dev-mode
missing-key writer (§3), writing `<base>/<language>/<namespace>.yaml`. `.env` points it at the
locale root. Two consequences:

- Neither checker consults it; the tools are independent.
- `update_translation_keys` does `std::env::var(...).unwrap()` (`:39`), so it **panics** if the
  variable is unset; the empty-string check on the next line (`:41-43`) is unreachable in that
  case. `.env` is git-tracked (ISSUE-004), so fresh clones inherit the author's relative path.

The namespace written by the dev writer comes from i18next, and the key uses `:::` as the
parent/sub-key separator (`translations_commands.rs:84-107`), matching `keySeparator` (§1).
Without `:::`, the key is inserted at the top level of the file (`:108-114`).

## 5. Languages

**Chinese only.** `zhCN` is the sole entry in `LANGUAGES`
(`packages/pastebar-app-ui/src/locales/languges.ts`), and `en` is retained as i18next's
fallback because it _is_ the key set (§1) — it is an implementation detail, not a language a
user can choose.

| Directory | Code   | Role                                               | Namespace files |
| --------- | ------ | -------------------------------------------------- | --------------- |
| `en/`     | `en`   | **`DEFAULT_LOCALE`** — key set + fallback          | 19              |
| `zhCN/`   | `zhCN` | **`DEFAULT_USER_LOCALE`** — the only user language | 19              |

The 19 namespace files: `backuprestore.yaml`, `calendar.yaml`, `collections.yaml`,
`common.yaml`, `common2.yaml`, `contextMenus.yaml`, `dashboard.yaml`, `help.yaml`,
`history.yaml`, `menus.yaml`, `navbar.yaml`, `pinned.yaml`, `settings.yaml`, `settings2.yaml`,
`specailCopyPaste.yaml`, `specialCopyPaste.yaml`, `templates.yaml`, `tours.yaml`,
`updater.yaml`.

This resolves the misspelling noted in earlier revisions: `specailCopyPaste.yaml`
(transposed `a`/`i`) exists **only** under this name, in both directories, and is a distinct
namespace from the correctly spelled one. `zhCN/specailCopyPaste.yaml` was added when the
catalogs were consolidated — the file had existed only in `en/`, so `t('Special Settings',
{ ns: 'specailCopyPaste' })` had been untranslatable. Do not "fix" the spelling without
changing the caller: the namespace is resolved by basename, so renaming the file alone
silently drops the string.

**Two defaults, and the difference matters.** `DEFAULT_LOCALE` is i18next's fallback and must
stay `'en'`. `DEFAULT_USER_LOCALE` is `'zhCN'` and is what an install gets when no language is
stored, or when the stored code names a language that no longer exists. An install upgraded
from a multi-language build still has e.g. `de` in `userSelectedLanguage`; falling through to
the i18next fallback would silently turn the UI English for someone who never chose English.
`App.tsx` therefore resolves the stored value through `isSupportedLocale()` and falls back to
`DEFAULT_USER_LOCALE`, and rewrites the stored value on the next first-run pass.

`javascript-time-ago` is registered for `en` and `zh` only; `locales.ts` maps the project's
short codes to BCP-47 (`zhCN` → `zh-CN`) for relative timestamps. The backend `Translations`
struct (§1) now carries `en` and `zhCN`; `get_lang()` returns `en` for any unrecognised code,
so a stale `de` yields readable English rather than a `Language 'de' not supported.` menu item.
